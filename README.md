# nOdes: a human-carried proximity swarm

nOdes is a swarm of handheld wireless "orbs" that sense **who is with whom** in a room
by inter-node radio signal strength, cluster on it, and play that configuration back
to the people holding them as collective light and sound. The orbs have no locomotion
of their own: their configuration (and everything downstream of it) is supplied by
the people carrying them.

This repository is a **curated replication kit**, not a mirror of the development
repo. It contains what you need to build the hardware, flash and update the
firmware, run the central plane, run the fleet with no central plane at all, and
reproduce the calibration results. It deliberately omits study material, ethics
documents, paper drafts, raw session captures and video.

If you use it, please cite the papers in [Citation](#citation).

## The system in one paragraph

Each orb is an ESP32-S3 with 12 APA102 LEDs, an LSM6DS accelerometer/gyro, an INA219
battery monitor, a speaker and a MEMS microphone, in a sealed shell. There is no USB
access once built, so **all updates are over the air**. Orbs broadcast to their peers over
ESP-NOW and log received signal strength, producing a proximity graph; an adaptive-gap
single-linkage clusterer turns that into cluster membership. The **same clustering
routine** runs in two regimes: **ad-hoc** (orbs only, peer-to-peer, no server, no access
point, and what ships to unattended installations) and **infrastructure mode** (an optional
Linux server sends a 50 Hz multicast frame carrying colour per slot, receives unicast
telemetry from every orb, and drives synchronised light and sound). The two share one
radio: an orb that has just received a multicast frame broadcasts its own neighbour
view 2 ms later, so the server's frame is a free fleet-wide pacer for the peer sensing.
When the server falls silent the orbs switch to a standalone pacer in about a second.

Architecture diagram: `docs/hardware/SystemDiagram_nOdes.drawio.pdf`.

## Hardware

Per orb (ESP32-S3, dual-core, two I2S peripherals):

| Function | Part | Pins |
|---|---|---|
| LEDs | 12 × APA102 on SPI2 | DATA GPIO18, CLK GPIO8 |
| Motion | LSM6DS on I2C0 | SDA GPIO9, SCL GPIO10, INT1 GPIO21 |
| Battery | INA219 on I2C0 | (shared bus) |
| Speaker/amp | I2S0 | DIN GPIO40, BCLK GPIO41, LRCK GPIO42 |
| Microphone | ICS-43434 on I2S1 | WS GPIO15, SCK GPIO17, SD GPIO16 |
| SD (unused; driver removed) | SPI3 | MOSI GPIO13, MISO GPIO11, SCK GPIO12, CS GPIO14 |

Exploded views of the orb and the charging station are in `docs/hardware/`. The
parametric enclosure design will be added to this repository; until then, note that
the shell is **sealed** and that this has consequences (see *Safety-critical
invariants*).

Access point: the deployments use a Ruckus R500 with multicast-to-unicast conversion.
Any AP that converts multicast to unicast will do; without conversion, expect the
downlink to starve above roughly ten orbs at 50 Hz (see *What the calibration found*).

**Network invariant:** the server must be `10.0.0.8`. The firmware hardcodes it.

## Build and flash the firmware

Requires ESP-IDF **v5.4** (not vendored here):

```bash
git clone -b v5.4 --recursive https://github.com/espressif/esp-idf.git
cd esp-idf && ./install.sh esp32s3 && cd ..

cd client
# set your own AP credentials first:
#   #define WIFI_SSID / #define WIFI_PASS in main/hello_world_main.c
source ../esp-idf/export.sh
idf.py build
ls -l build/espidf_orb.bin        # MUST be under 1 MB (see below)
```

**First flash of a new orb** is over USB, before the shell is sealed
(`tools/reflash-orb.sh` targets a CP210x jig). **Every update after that is OTA:**

```bash
cp client/build/espidf_orb.bin server/espidf_orb.bin
cd server && python3 -m http.server 8000     # orbs fetch http://10.0.0.8:8000/espidf_orb.bin
# in the server TUI, send command 0x01 to the target serial
```

`client/firmware-stable/` and `client/firmware-3.23/` hold the binaries that were
actually deployed to the fleet, with `SHA256SUMS`. They were built with the authors' AP
credentials compiled in and are provided as known-good reference images; build your own.

### Safety-critical invariants: read before touching firmware

- **OTA is the only update path and rollback is not enabled.** A bad OTA build bricks a
  sealed orb permanently. Bench-test on two or three orbs first.
- **The binary must stay under 1 MB.** The partition table cannot be changed without
  USB. The SD-card driver was removed to make room; do not reintroduce it.
- **New peripheral initialisation must be server-triggered, never boot-time.** A
  boot-time crash loop on a sealed orb is unrecoverable.
- **Do not drive the speaker from a boot-time path or at amplitude above ~16000.**
  Orb-local audio browns out the ESP32-S3 on a partly-charged battery and drops the
  radio. The acoustic-ranging line of firmware that did this is not in this repo.
- Core 0 runs Wi-Fi and a 5 s task watchdog on the idle task: any long loop on core 0
  must `vTaskDelay(1)` regularly. Never wrap `esp_wifi_sta_get_ap_info()` in
  `ESP_ERROR_CHECK`.
- The firmware's `compute_cluster_ids` **mirrors the server's** adaptive-gap
  flood-fill line for line. If you change one, change the other.

Full working rules: `docs/ENGINEERING_NOTES.md`. Version history and what is deployed:
`docs/FIRMWARE_HISTORY.md`, `docs/VERSIONS.md`.

## Build and run the central plane

```bash
# deps: cmake, g++ (C++17), ncurses, nlohmann-json, eigen3
cd server && mkdir -p build && cd build && cmake .. && make
./multicast_sender                 # 50 Hz, pinned to an isolated core under SCHED_FIFO
./multicast_sender --autorate      # adaptive send rate (recommended above ~10 orbs)
./multicast_sender --rate 20       # fixed rate
```

The server exports live state as JSON to `/tmp/orb_data`: slot↔serial map, proximity
matrix, per-orb telemetry, network stats. Everything else reads that file:

```bash
cd visualiser && python3 -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt
python3 proximity_graph.py         # live force-directed proximity graph
python3 cluster_viz.py             # movement-clustering visualiser (MODE_CLUSTER)
```

Sound: `sound/` holds the SuperCollider synths and the conductor; `sound/desktop/`
has the systemd units and PipeWire routing for a Linux workstation (`pw-jack`, 48 kHz/1024).

Running a session end to end (start order, audio debugging, capture verification)
is `docs/SESSION_RUNBOOK.md`. Pre-flight is `tools/session_preflight.sh`.

## Reproducing the calibration

`data/calibration-2026/` contains the run data behind the published calibration
(threshold sweep E2, smoothing grid E3, handover E6, anchored localisation E7, with
raw captures) and the figure script:

```bash
python3 tools/make_calibration_figs.py     # regenerates data/calibration-2026/figs/*.png
```

The deployment telemetry behind the topology-churn figure is not included by default;
the script skips that figure if the file is absent. Experiment drivers for re-running
each measurement on your own fleet are `tools/e2_threshold_sweep.py`,
`e3_stability_sweep.py`, `e4_drive.py`, `e5_coverage.py`, `e6_run.py`,
`e7_place.py` / `e7_verify.py` / `e7_localisation.py`; capture with `orb_capture.py`
and replay with `orb_replay.py`.

### What the calibration found

Design rules for RSSI proximity clustering on identical hardware, each measured:

- **Report about 8 neighbours** when groups are near the radio's resolution limit;
  6 suffice when they are well separated.
- **The threshold floor is inert below the adaptive cut** (~218 on the saturated
  scale). The only reachable failure is setting it too high; the band that binds and
  resolves is 218–236.
- **Smooth with an RSSI decay constant ≥ 3 s.** At-rest instability is exactly zero
  for every τ ≥ 3 s at every debounce setting.
- **Saturating the similarity widens the correct-threshold band** rather than harming
  clustering, and destroys the gradient that metric ranging would need. For a swarm
  whose useful percept is *who is with whom*, that is the right trade.
- **Three known-position anchors give station-level presence and bearing at range,
  not position** (radius compressed ~4.4×). Plan on relational sensing.
- **Above ~10 orbs, use the adaptive send rate.** A fixed 50 Hz starves a 26-orb
  fleet (84 % miss); autorate holds per-orb miss at ~8 % from 4 to 26.
- **A stationary fleet with no server sleeps after 30 s** and wakes on handling. The
  ad-hoc regime self-sustains while the swarm is in use.
- **Server-loss handover takes about a second**, and the accuracy the standalone
  regime gives up is predicted by the neighbour-count result.
